Sistema de Logging Distribuido

Manual Teórico — Fundamentos y Arquitectura

1. Introducción

Después de que el sistema anterior colapsara por falta de trazabilidad ("si nadie registró el error, técnicamente no pasó"), la misión fue diseñar un servicio de logging distribuido: un punto central donde cualquier servicio de la plataforma pueda reportar qué le está pasando, para poder diagnosticar fallas, medir el comportamiento del sistema y tener evidencia cuando algo se rompe.

Este manual explica los conceptos teóricos detrás de cada pieza del sistema construido, y cómo se conectan entre sí.

2. Qué es un log y por qué registrar todo

Un log es un registro cronológico de un evento que ocurrió dentro de un sistema: quién lo generó, cuándo, con qué gravedad y qué pasó exactamente. Todo log tiene cuatro datos mínimos:

  • timestamp: cuándo ocurrió el evento en el servicio de origen.
  • service: qué componente lo generó.
  • severity: qué tan grave es (DEBUG, INFO, WARN, ERROR, FATAL).
  • message: descripción humana de lo que pasó.

En sistemas con un solo servidor alcanza con escribir logs a un archivo local. En sistemas distribuidos (varios servicios o procesos corriendo en paralelo) eso no sirve: cada uno tendría su propio archivo, en su propia máquina, con su propio reloj. Si algo falla, hay que ir servicio por servicio buscando qué pasó. Un servicio de logging centralizado resuelve esto: todos mandan sus logs a un solo lugar, y desde ahí se puede reconstruir la historia completa de un incidente.

3. Arquitectura distribuida: clientes y servidor central

El patrón usado es "muchos productores, un consumidor": cualquier cantidad de servicios (clientes) generan eventos de forma independiente y los envían por red a un único servidor que los recibe, valida y guarda.

  • Los clientes no comparten memoria ni proceso entre sí: están desacoplados.
  • El servidor central es el único punto de escritura a la base de datos, lo que evita condiciones de carrera en el almacenamiento.
  • La comunicación entre clientes y servidor es por HTTP, el protocolo estándar para este tipo de integración porque es simple, universal y no requiere que cliente y servidor compartan tecnología.

4. HTTP y APIs REST

HTTP es el protocolo sobre el que funciona toda la web: un cliente manda una petición (request) a una URL, con un método y opcionalmente un cuerpo de datos, y el servidor responde con un código de estado y una respuesta.

  • POST: se usa para crear algo nuevo. En nuestro caso, insertar logs.
  • GET: se usa para consultar datos sin modificarlos. En nuestro caso, listar logs.
  • Cuerpo en JSON: formato de texto estructurado, liviano y estándar para intercambiar datos entre sistemas.
  • Códigos de estado relevantes: 200 OK, 201 Created (log guardado), 400 Bad Request (datos inválidos), 401 Unauthorized (token inválido o ausente).

Una API "REST" es una API HTTP organizada alrededor de recursos (aquí, el recurso es /logs) que usa los métodos HTTP con su significado convencional: POST para crear, GET para leer.

5. Autenticación con tokens

Autenticar significa que el servidor pueda confirmar quién está hablando con él antes de aceptar la petición. Sin esto, cualquiera podría mandar logs falsos o basura al sistema.

  • Un token es un string secreto que actúa como credencial: quien lo tiene, se asume autorizado.
  • Se envía en el header HTTP Authorization, no en la URL ni en el cuerpo, porque los headers no quedan expuestos en logs de proxies ni en historiales de la misma forma que una URL.
  • Formato usado: Authorization: Token <valor>. Es un esquema simple; existen esquemas estándar más completos (Bearer para JWT/OAuth), pero para este alcance una lista de tokens válidos es suficiente.
  • El servidor mantiene una lista de tokens válidos asociados a un servicio; si el token no está en la lista, rechaza la petición con 401 antes de tocar la base de datos.
Esto es autenticación, no autorización: solo confirma "quién sos", no decide "qué te dejo hacer" (en un sistema más grande, cada servicio podría tener permisos distintos sobre qué puede loguear).

6. Persistencia de datos: bases de datos y SQL

Guardar los logs solo en memoria no sirve: si el servidor se reinicia, se pierde todo. Por eso se usa una base de datos, que persiste los datos en disco de forma estructurada y consultable.

  • SQLite: motor de base de datos relacional que guarda todo en un solo archivo, sin necesitar un servidor de base de datos aparte. Ideal para un proyecto de este tamaño.
  • Tabla logs: estructura con columnas fijas (id, service, severity, message, timestamp, received_at). Cada fila es un log.
  • Índices: estructuras auxiliares que aceleran las búsquedas por columnas específicas (aquí, timestamp y received_at), para que filtrar por fecha no tenga que recorrer toda la tabla.
  • Transacciones: agrupan varias operaciones (por ejemplo, insertar 50 logs) para que se apliquen todas juntas o ninguna. Evita quedarse con datos a medias si algo falla en el medio.

7. Validación y calidad de datos

Antes de guardar cualquier dato que venga de afuera hay que verificar que tenga sentido. Sin validación, la base de datos termina llena de información inconsistente que rompe cualquier análisis posterior.

  • Se valida que timestamp sea una fecha real y parseable.
  • Se valida que service y message sean strings no vacíos.
  • Se valida que severity sea uno de los niveles conocidos (DEBUG, INFO, WARN, ERROR, FATAL).
  • Si un log del lote es inválido, se rechaza el lote completo (todo o nada), para que nunca queden inserciones parciales confusas.

8. Concurrencia y procesamiento por lotes

Un sistema de logging real puede recibir miles de eventos por segundo desde muchos servicios a la vez. El diseño tiene que soportar eso sin caerse.

  • El endpoint POST /logs acepta un log individual o un array de logs en una sola petición (batch), reduciendo la cantidad de conexiones HTTP necesarias.
  • Las inserciones de un lote se hacen dentro de una transacción SQL, mucho más rápida que insertar fila por fila con confirmaciones separadas.
  • Node.js procesa las peticiones de forma asíncrona (no bloqueante), lo que permite atender múltiples clientes en paralelo sin necesitar un hilo por conexión.

Qué significa "no bloqueante" en la práctica

Node.js corre en un único hilo, pero ese hilo nunca se queda "esperando parado" una operación de entrada/salida (red, disco). Cuando llega una petición HTTP, Node la empieza a procesar y, en el momento en que hay que esperar algo lento (que termine de llegar el body por la red, que el sistema operativo confirme una escritura), delega esa espera y sigue atendiendo otras peticiones mientras tanto. Cuando la operación lenta termina, retoma donde había quedado. A este mecanismo se lo llama event loop.

Esto es lo que hace posible este proyecto en particular: varios servicios simulados mandando requests casi en simultáneo, más una ráfaga de 1000 logs de golpe, sin que el servidor necesite abrir un hilo del sistema operativo por cada conexión (algo caro en memoria y CPU si se repite miles de veces). Un servidor puramente bloqueante tendría que terminar de atender una petición completa antes de poder empezar a leer la siguiente.

Matiz importante: el driver node:sqlite usado en este proyecto (DatabaseSync, como su nombre lo indica) es en sí mismo síncrono: mientras corre una consulta, sí bloquea el hilo. Como acá las consultas son locales (un archivo en disco, pocas filas) y muy rápidas, ese bloqueo es despreciable. Pero en un sistema con consultas pesadas o una base de datos remota, ahí sí sería un cuello de botella real — por eso en producción se suele usar un driver asíncrono (por ejemplo pg para Postgres) en vez de uno síncrono.

Por qué esto es relevante al elegir tecnología

No es que Node sea "más rápido" que otros lenguajes por naturaleza, sino que su modelo de concurrencia por defecto calza perfecto con lo que necesita un servidor de logging: muchas conexiones cortas, la mayoría del tiempo esperando I/O y no haciendo cálculo pesado. Si este mismo servidor se escribiera en Python con Flask (el framework sincrónico clásico), cada request ocupa un hilo/worker completo hasta terminar: si 1000 peticiones llegan casi juntas, se procesan de a una por worker disponible y el resto hace cola. Para lograr el mismo comportamiento no bloqueante en Python hay que elegir explícitamente un framework asíncrono como FastAPI y escribir los handlers con async/await sobre asyncio — en Node ese modelo viene por defecto, sin tener que elegirlo.

9. Arquitectura del sistema implementado

Flujo completo de una petición, de punta a punta:

  • 1. Un servicio simulado genera un log falso (timestamp, service, severity, message).
  • 2. Lo envía por HTTP POST a /logs, con su token en el header Authorization.
  • 3. El servidor Express recibe la petición y la pasa por el middleware de autenticación.
  • 4. Si el token es válido, pasa a la validación de los campos del log.
  • 5. Si los datos son válidos, se calcula received_at (momento en que el servidor lo recibió) y se inserta en SQLite dentro de una transacción.
  • 6. El servidor responde con 201 y los logs guardados, incluyendo su id.
  • 7. Para consultar, un cliente manda GET /logs con filtros opcionales por query string; el servidor arma la consulta SQL con esos filtros y devuelve los resultados ordenados por timestamp.
Nota clave: timestamp es la hora que reporta el servicio de origen (cuándo pasó el evento), mientras que received_at es la hora del servidor central (cuándo llegó el log). Pueden diferir por latencia de red, reintentos o relojes desincronizados entre servicios; por eso el sistema permite filtrar por ambas.

10. Recorrido por el código

server/index.js

Define el servidor Express y los dos endpoints principales.

app.post('/logs', authMiddleware, (req, res) => {
  const entries = Array.isArray(req.body) ? req.body : [req.body];
  const errors = entries.flatMap(validateLog);
  if (errors.length > 0) return res.status(400).json({ error: 'Logs invalidos', details: errors });
  const ids = insertLogs(entries.map(normalizeLog));
  res.status(201).json({ inserted: ids.length, logs: /* ... */ });
});

server/auth.js + server/tokens.js

El middleware de autenticación intercepta la petición antes de llegar al handler.

export function authMiddleware(req, res, next) {
  const [scheme, token] = (req.get('Authorization') || '').split(' ');
  const service = scheme === 'Token' ? resolveServiceFromToken(token) : null;
  if (!service) return res.status(401).json({ error: 'Quien sos, bro?' });
  req.authService = service;
  next();
}

server/db.js

Encapsula el acceso a SQLite: creación de la tabla, inserción en lote dentro de una transacción, y consulta con filtros dinámicos.

export function insertLogs(logs) {
  db.exec('BEGIN');
  const ids = logs.map(insertLog);
  db.exec('COMMIT');
  return ids;
}

clients/services.js + clients/simulate.js

Simulan servicios reales: generan logs falsos con severidades realistas (más INFO que FATAL) y los mandan al servidor, en modo tiempo real o en ráfaga para pruebas de carga.

11. Decisiones de diseño

DecisiónPor qué
SQLite nativo (node:sqlite) en vez de una base externaNo requiere instalar ni levantar un servicio de base de datos aparte; para el volumen de este proyecto es más que suficiente.
Tokens fijos en una lista manualLa consigna pide explícitamente una lista manual; en un sistema real se reemplazaría por tokens rotables guardados de forma segura.
POST /logs acepta uno o varios logsEvita que un servicio con mucho volumen tenga que abrir una conexión HTTP por cada línea de log.
Validación todo-o-nada por loteEl cliente siempre sabe con certeza si se guardó todo o nada; nunca queda en un estado ambiguo.
Se separan timestamp y received_atPermite detectar demoras de red o desincronización de relojes entre servicios.

12. Cómo se hace esto en sistemas reales

Este proyecto es una versión simplificada y didáctica de algo que en la industria se resuelve con herramientas especializadas:

  • ELK Stack (Elasticsearch, Logstash, Kibana): recolecta, indexa y visualiza logs a gran escala.
  • Grafana Loki: sistema de logging pensado para integrarse con métricas y dashboards de Grafana.
  • Colas de mensajes (Kafka, RabbitMQ): en vez de mandar logs directo por HTTP, los servicios los publican en una cola y workers los consumen y guardan, así el servidor de logging nunca se satura ni bloquea a los servicios que lo usan.
  • Autenticación real: en vez de una lista fija de tokens, se usan API keys rotables, mTLS o JWT firmados con expiración.

La arquitectura armada (servicios → HTTP → validación → base de datos) es el mismo esqueleto conceptual que estas herramientas, a una escala mucho más chica y sin las piezas de infraestructura adicional (colas, clusters, réplicas).

13. Glosario

Log
Registro de un evento.
Timestamp
Marca de tiempo de un evento.
Severity (nivel de severidad)
Qué tan grave es un evento.
Endpoint
Una URL específica de una API que atiende un tipo de petición.
Middleware
Función que intercepta una petición antes de que llegue al handler final (por ejemplo, para autenticar).
Token
Credencial secreta usada para autenticar.
Query string
Parámetros que van después del "?" en una URL, por ejemplo ?service=pagos.
Transacción
Conjunto de operaciones de base de datos que se aplican todas juntas o ninguna.
Batch / lote
Agrupar varios elementos en una sola operación.
Event loop
Mecanismo de Node.js (un solo hilo) que va turnándose entre tareas: cuando una tiene que esperar una operación de I/O, la deja en pausa y atiende otra, sin bloquear todo el proceso.
I/O no bloqueante (non-blocking I/O)
Modelo donde el programa no se queda "parado" esperando que termine una operación lenta (red, disco); sigue atendiendo otras tareas mientras esa operación se resuelve en segundo plano.
ACID
Propiedades que garantizan que las transacciones de una base de datos sean confiables (Atomicidad, Consistencia, Aislamiento, Durabilidad).
